# naqqa-auth identity lifecycle and data review (P-ATTACK rounds 6 and 7)

Scope: `auth/src/main/java` on branch `feat/naqqa-sso` after the fixes of round 6, reviewed from the data angle (what each collection holds, who reads and writes it, uniqueness, retention, secrets at rest, startup migrations) and from the identity lifecycle angle (every state transition of an account and what it revokes, keeps and audits). Tests are in `auth/src/test/java`; ids are `SSO-T-auth-<n>`. "Revoke all" below means `SsoCredentialRevoker.revoke`: SSO sessions and their refresh families, OIDC sessions (back-channel logout), every OIDC grant and refresh family including `offline_access` and its access tokens, tickets (remembered devices, link intents, enrollments, pending SAML and OIDC interactions), MFA tokens issued before now, magic links, push approvals, pending OTPs of the account's addresses, the pending password reset token of its address (F-CONF-27), and since round 6 the impersonation sessions the account started as an operator. It writes `credentials.revoke_all` with the reason.

Second-factor and password verification (MFA verify, step-up, OTP sign-in, erasure re-authentication, TOTP confirm, password sign-in) take a Mongo lease per account (`sso_ratelimit`, `ls:` keys, 10 s) for the whole check, verify and record sequence, and all of them except password sign-in count failures on the account key whatever the IP (10 failures, then `CHALLENGE_REQUIRED` for the decay window). Password sign-in from a known device keeps its per device and IP lease so an attacker cannot lock the owner out (SSO-T-auth-424, 610).

## 4. Residuals

- Removing a role does not revoke sessions; access tokens carry the old authorities until they expire (15 minutes) or are refreshed.
- OTP attempt counters use `$max` across nodes: two wrong guesses on two nodes at the same instant through two different paths can count once. Every path holds its per-account lease, the code space is 10^6 with 5 attempts.
- The registration attempt counter is a read-modify-write on the Redis record; a parallel burst on one pending registration can evaluate more than 5 guesses of the 62^6 code space before the record dies.
- Without a pepper (legacy mode only) the registration code is stored as SHA-256 (`s:`), keyed HMAC (`m:`) otherwise; SSO mode always has the pepper.

## 5. Round 7: case-duplicate emails, single-use codes across nodes

Email index migration (F-A6-AUTH-10). `UserEmailIndex.migrate` runs at startup in both modes (`SsoMongoIndexes.ensureCore`) and from `POST /api/sso/admin/users/email-conflicts/scan`:

1. If `users.email_ci_unique` exists, nothing to do (markers are cleared).
2. Otherwise an aggregation with the index collation (en, strength 2) groups string emails and keeps groups of two or more accounts. Without groups the index is created; a duplicate written meanwhile makes the creation fail, which is caught and re-checked, so startup never fails.
3. With groups the index is not created. The oldest account of each group (lowest id, ids come from the users sequence) is canonical; every newer account gets a `sso_email_conflicts` marker. Startup logs one warning with counts only (groups, accounts), never addresses. Several nodes starting at once run the same idempotent steps (marker upserts by id, index creation is idempotent), SSO-T-auth-620.

Behaviour while duplicates exist: every email lookup resolves to the canonical (oldest) account whatever case is typed, for password, OTP, magic link, passkey options, password reset, LDAP, social and SAML. The older owner is never locked out, and nobody can reach a newer duplicate by email, which is the only ambiguous identifier; a newer duplicate keeps its sessions and its non-email sign-ins (usernameless passkey, linked social subject) because those identify it without ambiguity. New writes keep the application check (`emailTaken`, collated) so no new duplicate is created. The admin view of a newer account shows `emailConflictWith`; `GET /api/sso/admin/users/email-conflicts` lists groups. An operator moves a newer duplicate to its own address (`POST /api/sso/admin/users/{id}/email`, step-up, audited, verification cleared) or erases it; the migration then runs again and creates the index once no group is left. Merging accounts is out of scope.

Single use across nodes (F-A6-AUTH-9). The core services stay node-local (`synchronized`); the Mongo stores make the decisive write conditional: an OTP challenge is consumed or counted only while `consumed=false`, and a recovery code is marked used only if the stored code hashes and used flags still equal the state read for this redemption. A lost race raises `OptimisticLockingFailureException`, which `SecondFactors` treats as a failed code. SSO-T-auth-619 runs two application contexts on one database and presents one email OTP (OTP sign-in on node A, step-up on node B) and one recovery code (MFA verify on A, step-up on B) to both at the same instant: one is accepted.

## 6. Confirmation rounds 4 and 5: identity control matrix

Every event that changes who controls an account, or what it holds, is checked against every credential the account can hold on another device, each obtained through its real flow. SSO-T-auth-772 (`IdentityControlMatrixTest`) runs each event on a TOTP account with a phone number and then uses each credential; the event without change shows that every check accepts a valid credential. | Erasure | `DELETE A/users/{id}` | R | R | R | R | R | R | R | R | R | R | R | R |

A user link, a social auto-link and a SAML adoption add a sign-in method without removing one: whoever held the account keeps it and gains nothing from a revocation, so they keep every credential. A role grant or removal and a recovery code regeneration change what the account may do or replace a factor's secrets, not who controls it; the access tokens in flight carry the previous authorities until their refresh (section 4), where an account that became administrative without a strong factor gets the restricted enrollment session (`assurance-model.md` section 3). Revoking the other sessions signs other devices out: it ends their sessions, refresh families, remembered devices and the codes they hold, and keeps the `offline_access` grants (an application consent, revoked per grant or by any revoke all) and the pending mailbox, SIM and push proofs, which are not sessions.

Events outside the matrix: the admin resolution of a case-duplicate email (`POST A/users/{id}/email`, section 5) moves only a newer duplicate, which never received a mailbox credential and cannot sign in by email, and keeps its sessions (SSO-T-auth-617); tenant administrator membership (`admins` of `sso_tenants`, set through the tenant admin API) acts like a role, read on every admin request, so a removal takes effect at once without revoking anything; an enable restores nothing; unlock and impersonation change no credential; the phone number has no write path in naqqa-auth. API tokens (`sso_api_tokens`) belong to a tenant, not to the account that issued them: they never act as the account and are not touched by its events. Pending registration codes exist only before the account (a confirm refuses an address taken in any case).
