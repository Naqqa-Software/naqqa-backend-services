# naqqa-auth federation: social, SAML SP and LDAP (P-ATTACK round 13)

Scope: `auth/src/main/java` on branch `feat/naqqa-sso` after round 13. Three upstream identity types can sign a person in to a local account: social and enterprise OIDC or OAuth providers (`SocialLoginController`, `AccountLinkService`), the tenant SAML IdP with naqqa as SP (`SamlSpController`, `SamlSpAccounts`, `SamlIdpAdminController`) and LDAP or Active Directory password binds (`DirectoryLogin`). This document states, per type, how an upstream identity reaches an account and what a later change does to the link and to sessions. Tests are in `auth/src/test/java`; ids are `SSO-T-auth-<n>`. "Class" is the account class of `assurance-model.md` (1 without a strong factor, 3 with TOTP or HOTP, 4 with a passkey).

Removing a link ends the sessions of the account (F-CONF-25): a user unlink revokes all except the current session, a platform removal of the IdP or of its last allowed domain and trust revokes all for every account it unlinked, and a directory adoption revokes all (F-CONF-26). Otherwise sessions are not tied to the upstream identity: removing one domain of several, removing the trust, or changing a directory leaves sessions already issued until they expire, are signed out or a revoke all ends them (a factor change, password reset, email change, disable, erasure or admin action).

## 3. Residuals

- Sessions issued through a federated sign-in are not revoked when one allowed domain of several or the trust of an IdP goes away; removing the link itself (unlink, IdP removal, last grant revoked) revokes them (section 1, last paragraph).
- An administrative account linked to a social provider still uses it as a first factor, like its password. Since F-CONF-16 an account holding an administrative role or authority needs MFA by default (`naqqa.sso.mfa.required-for-admin=true`, TOTP and recovery codes on by default): with an enrolled factor a social, SAML SP or LDAP sign-in asks for it; without one the federated sign-in ends in a restricted session limited to enrolling a factor (403 `MFA_ENROLLMENT_REQUIRED` elsewhere, the success redirect carries `#mfaEnrollment=1`), exactly as a password sign-in (`assurance-model.md` section 3); the app profile route (`mfa.enrollment-profile-routes`, default `GET /api/profile/me`) answers with `mfaEnrollmentRequired: true` while restricted, so the app detects a federated return that carries no login body. Social providers are platform configured, unlike tenant IdPs.
- LDAP has no deprovisioning sync: an entry removed from the directory stops password binds but not the other sign-in methods of the account (mailbox, passkey, social link).

## Facebook (F-E18, F-E19)

Facebook returns an email but never says it is verified, so `FacebookProfile` always sets `emailVerified=false`. Rules: (1) with `create-accounts` on, Facebook may create a new account, email stored unverified, link origin `unverified`; (2) Facebook never links to or adopts an existing account by email (`LINK_REQUIRES_LOGIN`), even with `auto-link` or `trust-all-emails` on; a verified Google or Apple sign-in cannot adopt an unverified Facebook-created account either; (3) an existing account links Facebook only from its own session after step-up (`POST /account/links/facebook/start`, then `/oauth2/authorization/facebook?link=`), with origin `user`; (4) the flag flips only through mailbox proof in the existing flow (magic link or email OTP sign-in, `SsoAccounts.markEmailVerified`); a Facebook sign-in is `fed`, strength 1, and the account MFA policy follows as for any provider; (5) when the flag flips, an `unverified` Facebook link stops signing in so a pre-registered identity cannot outlive the mailbox owner taking over the address. The debug_token URL is configurable (`debug-token-endpoint`, default the pinned `v19.0` Graph URL), under the same SafeHttp rules as every provider URL. Tests: auth 740 to 744, sso 236.
